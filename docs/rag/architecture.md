# 구조

## 책임

| 구성 요소 | 역할 |
|---|---|
| 온통청년 Provider | 공고 ID로 실제 API 원본을 다시 조회 |
| 본문 변환·청크 분할 | 확인된 항목을 정리하고 검색 문단 생성 |
| OpenAI Embedding Client | 텍스트를 벡터로 변환, 반환 차원·순서 검증 |
| PostgreSQL Repository | 원본·버전·청크·처리 상태 저장, 활성 공고 범위 검색 |
| RAG Service / Controller | 색인·상태 조회·근거 검색 API |
| Scheduler | 설정한 공고 ID의 주기적 갱신 |
| 대화 담당 기능 | 세션·이전 대화 처리, 검색 질문 작성, LLM 호출과 답변 표시 |

## DB의 의미

PostgreSQL 하나에 일반 데이터와 벡터를 함께 둔다. pgvector는 PostgreSQL의 벡터 저장·유사도 검색 확장이다. 임베딩 API는 벡터만 반환하며 우리 검색 DB를 만들어주지 않는다.

- 원본: 온통청년의 JSON, 출처 URL, 수집 시각.
- 문서 버전: 정리한 전체 본문, 본문 해시, 임베딩/분할 설정.
- 청크: 문서에서 나눈 조각, 제목/섹션, 순서, 벡터.
- 처리 상태: 진행 중 여부, 마지막 성공/실패. 원래 예외나 키는 저장하지 않는다.

저장소의 실제 스키마는 `backend/src/main/resources`의 RAG migration을 기준으로 한다. DB migration은 RAG를 켰을 때 실행한다.

## 검색 경계

공고 ID와 활성 버전, 모델·차원이 맞는 청크만 후보가 된다. 다른 공고에서 검색한 뒤 프론트가 걸러내는 구조로 만들지 않는다. 모델 변경 후 기존 벡터를 그대로 사용하지 않는다.

사용자 질문은 검색 요청을 처리하는 동안만 사용한다. 질문 원문과 대화는 RAG DB에 저장하지 않는다. 공개 원문도 관리 API를 통해 무제한 노출하지 않는다.

## 대화 담당 팀원과 연결

1. 세션에 선택한 `programId`를 연결한다.
2. 질문마다 검색 API를 호출한다. “그건 어디서 해?”는 이전 대화를 반영해 “해당 공고는 어디서 신청하나요?”처럼 명확하게 정리한다.
3. 근거 문단·출처와 이전 대화를 답변 LLM에 전달한다.
4. 반환된 문단에 답이 있는지 확인하고, 없는 정보는 확인되지 않는다고 답한다.

검색 점수가 높아도 답이 반드시 포함된 것은 아니다. 공고 텍스트는 사실 근거로 취급하고, 그 안의 문장을 시스템 지시로 실행하지 않는다.
